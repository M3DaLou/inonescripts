VPS Netcheck v1.5.0
全面审查与改进方案

结论：脚本覆盖面不错，适合作为人工排障入口；当前主要短板是证据保存、故障归因与系统修改的可靠性。全面改进应先修正误判和修复机制，再扩展检测项目。现版本不宜作为无人值守自动修复工具。

本报告记录原版审查、可复现缺陷与完整开发路线。后续已据此实现 v2 候选版本，具体已实现范围、测试及保留限制见新版使用说明；下文路线并非全部已实现。没有在生产 VPS 上执行原脚本，也没有执行真实系统修复或第三方检测代码。

2. 现有设计：值得保留什么

模块当前实现评价
交互 / CLI菜单、quick/full、指定 URL / DNS / IP、独立检测模式入口友好，但解析、校验与执行计划需要统一。
基础排障系统负载、时间、地址、DNS、ICMP、MTU、IPv6、端口、HTTPS排障顺序合理；多数问题来自判断逻辑过强、证据太少。
网络质量ping、TCP 建连、多跳 mtr / traceroute很有价值，应保留并优先修复目标识别及采样统计。
专项检测下载测速、Telegram、第三方流媒体适合可选模块，需要明确数据来源、测量范围和费用预算。
修复IPv6、MTU、DNS、gai.conf、MSS、NTP、DNS 缓存独立确认机制值得保留；回滚、错误传播、系统管理器识别不足。
实现习惯函数分区、部分数组引用、部分超时、HTTPS 并发五路、临时目录可作为重构基础。无需为了“全面”直接换语言或全部推倒。

5. 建议的下一版结构

保留 Bash 作为运行入口，源码模块化，发布时可打包成单文件。这样保留 VPS 上易用的一键入口，又避免把解析、采集、归因、修复继续混在一个控制流中。是否引入 Python 应由目标系统兼容范围决定，不必一开始强制要求。JSON 可用 jq 构建，绝不能靠未转义字符串拼接。

CLI / 菜单
    ↓ 同一套参数校验与执行计划
环境与能力检测 → 统一上下文（地址族、resolver、proxy、接口、预算）
    ↓
采集器：DNS / ICMP / TCP / TLS / HTTP / PMTU / 路由 / 下载
    ↓ 只产出证据，不写系统
规则层：事实 → 推断 → 置信度 → 建议
    ↓
输出层：终端 / JSON / 脱敏报告 / 与历史结果比较

独立修复层：计划 → 保存前态 → 应用 → 验证 → 提交或回滚

目录建议：bin/ 入口，lib/core/ 上下文与执行器，lib/probes/ 采集器，lib/rules/ 归因，lib/repair/ 事务，data/ 端点配置，tests/fixtures/ 原始工具输出，dist/ 发布文件。

统一结果协议

{
  "schema_version": "1.0",
  "probe": "https",
  "target": "https://example.com/",
  "family": "ipv6",
  "resolver": {"mode": "system"},
  "proxy_mode": "direct",
  "status": "WARN",
  "transport": {"tcp": "ok", "tls": "ok", "curl_exit": 0},
  "http_status": 403,
  "observation": "TLS 成功，站点拒绝本次 HTTP 请求",
  "diagnosis": null,
  "confidence": "high",
  "repair_recommendations": []
}

示例中 high 仅指“观察到 403”这一事实，不是“被封 IP”的置信度。缺失数据用 null，不能冒充 0。实际还应记录 run_id、时间、耗时、原始输出引用、工具版本、local_ip/remote_ip、重定向、attempted/succeeded/failed 和采样口径。

状态采用 PASS / WARN / FAIL / UNKNOWN / SKIP；UNKNOWN 表示证据不足，SKIP 表示未执行或条件不满足。区分“探测目标失败”和“工具执行失败”，避免把缺工具计为网络不通。

统一命令执行器

  • 每个任务保存 argv、开始/结束时间、退出码、stdout、stderr；设置连接超时、任务时限和全局时限。
  • 控制并发，测速与高频时延测量尽量隔离，避免测量流量自己制造拥塞。
  • 统一 locale；探测命令使用参数数组，URL 使用 scheme 白名单、禁 glob、参数分隔；避免 eval 和拼接 bash -c。
  • 对 curl 功能作版本/能力检测。不能假设老系统支持所有 write-out 字段、HTTP/3 或某个 DNS backend；缺能力明确降级。
  • 所有 DNS 与地址族选择显式生效；重定向逐跳记录，无法维持指定策略时明确失败/降级，不能静默切换。

修复事务必须满足的条件

  1. 独立的 repair plan 展示具体文件、接口、规则、影响范围及验证条件。
  2. 保存原始值、权限、所有者、链接及文件内容；状态放入受保护且唯一的运行目录。
  3. 串行加锁并校验变更前状态；只有明确选择的修复动作可以应用。
  4. 一次修改后立即检查真实生效状态；持久化与当前运行状态分别验证。
  5. 涉及 SSH 入口、IPv6、DNS、MTU 的变更提供延时自动回滚；不以单一公网站点恢复正常作为唯一提交条件。
  6. 显式 commit 后取消回滚；失败、掉线或未确认则恢复前态；撤销不得删除他人规则。

可提供 repair apply --plan plan.json、repair rollback --run-id ...；这些是建议的未来接口，当前原版并不支持。

6. 功能扩展：按用途分层

层级建议能力边界
第一层：基础可信度IPv4/IPv6 对照；A/AAAA 与 NSS；TCP、TLS、HTTP 分层；真实目标路由；代理模式；JSON；总预算优先落实，覆盖最常见且可证实的问题。
第二层：链路诊断指定端口/接口/源地址；多样本中位数与分位数；PMTU/tracepath；实际 conntrack 与内核计数增量；历史差异单侧追踪只能描述观测到的前向路径，不能单凭它给回程线路下结论。
第三层：业务专项可维护的 Telegram 端点；流媒体适配器；TLS 版本/证书；可选 HTTP/2、HTTP/3、DoT、DoHHTTP/3 需要工具实际支持；curl 不执行网页 JavaScript，不能等同浏览器业务验证。
第四层：多视角观测用户侧代理对比、受控远端探针、可选 iperf3 服务、不同时间窗口比较端到端/回程/最大吞吐需要相应对端或测量视角；公网 IP 地理库不能证明线路等级。

建议默认检测不修改系统、不自动安装包、不自动跑第三方代码。下载测速和流媒体作为显式选项，并预先显示时长/流量预算。兼容性先做好 Debian/Ubuntu 与 systemd，其他发行版、Alpine、容器环境以能力矩阵逐步扩展。

7. 分阶段实施与验收

阶段范围可验收结果
A：可信基础修复F01–F10；参数验证；默认不安装；保留原始错误；取消与清理15 个复现用例转为正确行为断言；403 不触发 IPv6 修复；未达目标不报已到；修复失败不能显示成功；失败状态有明确退出码。
B：采集与报告重构统一 DNS/地址族/代理/接口；结构化结果；工具能力检测；真实 conntrack；流量与时间预算同一目标各模块实际 IP、接口与协议一致；JSON 可被解析且缺测为 null；系统 DNS 回退可追踪；每项测量有 raw evidence。
C：可回滚修复配置管理器识别、快照、互斥动作、所有权标记、延时回滚、幂等第二次应用无重复资源；撤销恢复原值且不动他人配置；写失败/服务失败/连接断开测试都可恢复。
D：专项与发布TG、流媒体、TLS/HTTP 扩展；端点版本；发布校验；文档第三方链固定且记录版本；明确可用/受限/未知；慢源、失败源和取消均受预算约束；发布物来源可追溯。

建议先发布兼容旧参数的修正版本，再发布新架构版本；不要在同一轮同时改 CLI、所有检测算法、所有修复机制和发行版范围。

必备 Linux 测试矩阵

  • 网络：IPv4-only、IPv6-only、双栈、ICMP 禁用但 HTTPS 通、IPv6 无路由、IPv6 403、DNS 不通、NXDOMAIN、CNAME、多 A/AAAA、UDP 53 失败但 TCP 成功。
  • HTTP/TLS：证书过期/不匹配、代理存在、跨域重定向、自定义端口、429/500/503、超时但已有部分数据、大正文与慢流。
  • 质量：末跳不是目标、全星号、ECMP、目标 ICMP 限速、仅 80 端口开放、mtr 不支持 TCP/JSON、单次成功多次失败。
  • 系统：普通用户、root、缺 CAP_NET_RAW、容器无 systemd、只读 /etc、多默认路由、PPP、非英文 locale、缺工具。
  • 修复：resolv.conf 普通文件与符号链接、预存 MSS 规则、原 MTU 非 1500、原 IPv6 已关闭、配置写入失败、服务重启失败、重复应用、SIGINT/SIGTERM、回滚期间外部改动。

单元测试用固定夹具；网络行为用 Linux network namespace/netem 与受控 DNS/HTTP 服务；系统修复在一次性虚拟机测试。当前 Windows/Git Bash 的 15 项隔离复现只覆盖逻辑回归，不代替以上验收。

8. 使用入口与审计注意事项

用户提供的 bash <(curl -fsSL ...) 会执行下载到的内容；下载失败状态也不直接等同外层 bash 状态。开发审查建议采用“下载固定版本 → 校验 → bash -n → 显式执行”的入口。即使顶层脚本固定了版本，内部执行远程 main 的依赖仍需另行固定和审查。

日志默认包含公网/内网 IP、主机名、路由、URL 等信息；分享报告应脱敏 URL 用户信息、query token、代理密码及内部地址。保留本机完整私有报告，另生成可分享副本。最终建议说明清楚“检测发生在哪个网络命名空间、是否经代理、哪个地址族、哪个目标、哪个时间窗口”。

9. 核验资料

  • 本次审查的固定源码：以上缺陷的主证据。
  • curl 官方手册：时间字段、退出码、代理环境、配置与解析选项。在线文档对应较新版本，实施时须检测目标系统版本。
  • mtr 官方项目及手册：逐跳探测、响应限速及输出能力。
  • Linux man-pages：gai.conf：自定义 precedence 对默认表的影响及 glibc 适用范围。
  • Telegram 官方 DC 文档：入口 IP/port 可变化，普通 DC、媒体连接和 CDN 的区分。
  • RegionRestrictionCheck 当前源码：本次只抽查集成相关路径，未对该项目作完整安全评估。

本报告的重点是把“看起来像故障”转换为“有可核对证据的结论”，并确保每一个系统改动可验证、可追踪、可恢复。
